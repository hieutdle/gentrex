# Benchmark design

gentrex-bench measures how often Gentrex gets a genetic test report right,
and which command loses a value when it doesn't. It runs on synthetic reports
now, and later on real reports that two people annotate. The same scorer
will score both.

The generator of synthetic reports is built, and
[gentrex-bench/README.md](../../gentrex-bench/README.md) explains how to run
it. The scorer and the work on real reports are still to come.

## What it takes from other benchmarks

The design borrows from benchmarks in other fields. The last column says
whether gentrex-bench does it yet.

| Benchmark | What it does | What gentrex-bench does with it | Built |
| --- | --- | --- | --- |
| [TPC-H](https://www.tpc.org/TPC_Documents_Current_Versions/doc/tpc-h_v3.0.1.docx), for databases | Its `dbgen` program makes the same test data on every machine from a fixed seed. | `generate.py sample` makes the same cases from the seed in `settings.yaml`. A test checks this across two Python processes. | yes |
| TPC-H | Every published result comes with a [Full Disclosure Report](https://www.tpc.org/results/fdr/tpch/hpe~tpch~30000~hpe_proliant_compute_dl580_gen12~fdr~2026-06-11~v02.pdf) of the hardware, the settings and the price. | `manifest.json` records the settings and a checksum of each reference file. Each truth file records the model that wrote the report and the Chrome version. | for the generator |
| TPC-H | Its run rules forbid code that only exists to win the benchmark. | Nothing in Gentrex may react to what only synthetic reports have, such as their footer. | rule only |
| [Artificial Analysis](https://artificialanalysis.ai/methodology/intelligence-benchmarking), for LLMs | It runs every model itself with the same test setup, repeats the tests whose scores vary, and gives 95% confidence intervals. | Every model goes through the same Gentrex commands on the same frozen test set, three times, with bootstrap confidence intervals. | no |
| Artificial Analysis | It shows each model's accuracy next to its speed and price. | A plot of report accuracy against GPU-hours per 1,000 reports. | no |
| [GIAB and GA4GH](https://pmc.ncbi.nlm.nih.gov/articles/PMC6699627), for variant calling | Every tool's variants are matched and counted the same way. A variant found with the wrong genotype counts apart from one not found. | The scorer matches variants by gene and DNA change first, and then scores zygosity, classification and the rest. | no |
| GIAB and GA4GH | Results are split by variant type and region. | Every case records its lab, test, result and challenge tags, so results can be split by each. Each tag is in 21 to 23 of the 200 test cases. | yes |
| GIAB and GA4GH | Only regions where the truth is certain are scored. | Where a real report is ambiguous, the annotators give both readings and either one counts. | no |
| [CAMI](https://pmc.ncbi.nlm.nih.gov/articles/PMC6368784), for metagenomics | One simulation gives the truth for every step of the analysis. | One truth file holds the page texts for `gentrex transcribe`, the record for `gentrex extract` and the IDs for `gentrex normalize`. | yes |
| [n2c2](https://pmc.ncbi.nlm.nih.gov/articles/PMC7489085), for clinical NLP | Two people annotate each document, and a third settles disagreements. Matches are scored strict and lenient. | The same protocol for real reports, and both ways of matching. | no |
| [Weber et al. 2019](https://pmc.ncbi.nlm.nih.gov/articles/PMC6584985), guidelines | Simulated data has a known truth, but it must look like real data. | The truth comes from real ClinVar, HPO and MONDO records. Reports have distractors, held-out labs and scanned copies. Real reports will show how far synthetic results carry over. | partly |

Two ideas don't carry over. TPC-H scales its data up because databases slow
down as data grows, but Gentrex reads each report on its own, so 200 reports
show its speed as well as 10,000 would. Artificial Analysis also combines its
tests into one index. Gentrex would need weights between its measures for
that, and there is no good reason for any choice of weights, so report
accuracy stays the main number.

## Closest earlier work

[Yu, Weile and Courtot](https://www.medrxiv.org/content/10.64898/2026.01.19.26344287v1.full)
(OICR, medRxiv, January 2026) made 1,000 molecular test reports from seven
LaTeX templates, with text generated by code, and a "faxed" copy of each.
GPT-4.1-mini reached an average F1 of 55.6 on them, and the best local model,
Gemma 3, 41.3. The faxed copies lowered F1 by 38.8%.

They didn't test real reports, and they averaged F1 only over answers that
were valid JSON. A model that often fails to answer looks better that way.
Their generator is on GitHub at
[courtotlab/PDF_benchmarking](https://github.com/courtotlab/PDF_benchmarking),
so Gentrex can also be run on their reports.

## Generator

The truth of a case is fixed before any text is written. Code picks the
values, and a language model then writes a report that prints them. If the
model wrote the truth along with the report, it could contradict itself,
with a protein change that doesn't follow from the DNA change, or a table and
a paragraph that give different zygosities.

![The five steps of the generator. Code and a seed sample the case and write the truth file. An LLM writes the report as HTML, and Chrome renders it as a PDF. check.py compares the PDF text with the truth file, and a case that fails is written again. The PDFs that pass are scanned at two levels with Pillow, so each report comes as a native, scan, fax or mixed PDF, all with one truth file.](../images/benchmark-generator.svg)

The variants come from ClinVar, so their HGVS, classification, HGNC ID and
MONDO ID are real. The patient's features and the mode of inheritance come
from HPO's annotations of the variant's condition. The zygosity follows from
the inheritance and the patient's sex.

The model writes HTML, because language models write HTML and CSS well, and
it gives each lab its own layout. Gentrex reads PDFs, though, and its first
step, `gentrex transcribe`, is where real reports go wrong, in wrapped table
cells, columns and scanned pages. Headless Chrome prints the HTML to PDF.
WeasyPrint could do the same without a browser, but it supports less CSS.

The check reads the PDF's text with pdfplumber, as `gentrex transcribe` does,
and looks for every true value and every distractor. A report that misses
one is written again, up to three times. Nobody edits a truth file by hand.

Every report also comes as an image-only PDF at two levels of damage,
`scan` and `fax`, made with Pillow and numpy from a seed. The same PDF always
gives the same copy. A mixed PDF has about a third of its pages scanned. To
check that the damage looks real, print and fax 20 reports once, and compare
their OCR errors with those of the two levels.

The writing model must not be a Gemma model, because Gentrex extracts with
Gemma and would then read text that its own model family wrote. Any other
model on an OpenAI-compatible server works, on your own GPUs or hosted. A
hosted model is fine here, because the reports hold no patient data.

## Benchmark set

The first version has 300 cases from 8 fictional labs. Each lab has its own
layout and wording, such as "Pathogenic (Class 5)" or "VUS".

| Part | What it is |
| --- | --- |
| Dev set | 100 cases, for tuning Gentrex's prompts and settings |
| Test set | 200 cases, frozen. At 90% accuracy, 200 reports give a 95% confidence interval of about ±4 points, and at 70% about ±6. |
| Labs | Two of the 8 labs appear only in the test set, to show how Gentrex does on layouts it wasn't tuned on. |
| Versions | Each report comes as a native PDF, a scan, a fax and a mixed PDF, all with one truth. Comparing them shows what scanning costs. |
| Version name | A folder name such as `v1`. Results compare only within one version. |

A canary string in every file is planned. It's a fixed random string, as
BIG-bench uses, that lets model makers keep the set out of their training
data.

## Truth files

Each report gets one JSON file, in the formats Gentrex itself writes.

| Key | Holds |
| --- | --- |
| `case` | The split, lab, test, result, challenge tags and writing model |
| `record` | What `gentrex extract` should write, with the page of each variant |
| `normalized` | What `gentrex normalize` should add |
| `pages` | The text of each page of the native PDF |
| `distractors` | Values the report prints that must not be extracted |

Annotators will fill the same file for real reports, without `pages`, so one
scorer serves both.

## Scorer

The scorer isn't built yet. It will read a folder of truth files and a run of
Gentrex, and write tables and a JSON file with every detail. It goes in
`gentrex-bench/scorer/`.

### Counting

Every field of every report counts as one of these:

| Truth | Gentrex | Counts as |
| --- | --- | --- |
| value | same value | correct |
| value | null | missed |
| null | value | extra |
| value | other value | wrong, which is both missed and extra |
| null | null | correct |

A strict match needs the exact text. A lenient match ignores case, spacing
and trailing punctuation, and accepts HGVS written another way, such as
`c.5266dupC` for `c.5266dup`. Fields with a fixed list of values compare the
category. `overall_result_raw` is compared through its category, because
there's no single right place for the copied text to end.

Variants are matched one to one by gene and DNA change, and each matched pair
is then scored on its other fields. An extra variant is a distractor error if
the report prints it as a distractor, and a hallucination if it doesn't.
Clinical features match by text for `gentrex extract` and by HPO ID for
`gentrex normalize`.

### Main numbers

Report accuracy is the share of reports with nothing clinically wrong. The
result category is right, every variant's gene, DNA change, classification
and zygosity are right, and no variant is extra.

The scorer also gives the variant F1, with misses and extras split by cause,
and the share of reports with both the MRN and the date of birth right,
because a wrong MRN files the result under another patient. A table gives
the accuracy of every field.

### Where errors come from

Each lost value is charged to the first command that lost it:

| The value is | Charged to |
| --- | --- |
| missing from the transcribed text | `gentrex transcribe` |
| on a page that wasn't kept | `gentrex select` |
| wrong or missing in the record | `gentrex extract` |
| given the wrong ID | `gentrex normalize` |

Results are split by PDF version, by seen and held-out lab, by challenge tag,
by number of variants and by result.

### Statistics and cost

Confidence intervals come from a bootstrap that resamples whole reports,
because the fields of one report aren't independent. Two setups are compared
on the same reports. The final setup runs three times, to show how much runs
differ. A record with an `error` counts as all missed, and is never dropped.

The scorer records the GPUs, the time each command took and the GPU-hours per
1,000 reports. Gentrex doesn't save token counts yet. Saving the counts that
the model server returns is a small change.

## Run rules

1. Tune on the dev set only. Score the test set only for the numbers you
   report.
2. Report every run, not only the best one.
3. Use the same settings for native and scanned reports.
4. Nothing in Gentrex may react to what only synthetic reports have, such as
   their footer.
5. Keep with every result the Gentrex version and commit from `run.yaml`, the
   settings, the models, the vLLM version, the GPUs and the benchmark
   version.

## Real reports

Only real reports show how accurate Gentrex is in practice. 150 annotated
reports give about ±5 points at 90% accuracy.

Take them at random, from all labs and from both native and scanned PDFs,
and from reports nobody looked at while building Gentrex, such as a later
time window. Two people annotate each report from the PDF, without seeing
Gentrex's output, because people tend to accept what they're shown. A genetic
counselor settles their disagreements. Scoring one annotator against the
other gives the human ceiling.

The scoring runs on [Minerva](../minerva/minerva.md), and only the summary
tables leave it, because the error lists quote patient data.

Synthetic accuracy describes only the mix of cases that was generated. What
the synthetic set can show is whether it ranks setups the same way as real
reports and finds the same weak fields. Where it doesn't, the generator is
missing something, and that gap becomes a new challenge tag.

## Next steps

1. Generate the first two reports with a real model and read them. Then
   build the full set.
2. Write the scorer, with tests that score the truth against itself as 100%
   and count planted errors where they belong.
3. Run Gentrex on 20 cases as a pilot. Fix the generator where it's wrong,
   not Gentrex.
4. Freeze version 1 and run the final setup three times.
5. Get ethics approval, then annotate and score the real reports.

Who annotates the real reports is still open. Two people and a genetic
counselor would be ideal.
